# リモートワークスペース

[English](../remote-workspaces.md) · [简体中文](../zh/remote-workspaces.md) · [ドキュメント](../../README.ja.md)

リモートワークスペースでは、エージェント、ツール、セッションを Linux ホスト上で実行し、全画面の端末 UI を手元のコンピューター上で実行します。接続には SSH を使い、ファイルシステムのマウントやプロジェクトの同期は行いません。デフォルトでは、モデルリクエストはローカルのプロバイダー接続を経由し、プロバイダーキーはローカルに留まります。

## 要件

- 手元のコンピューターにシステムの OpenSSH（`ssh`）があり、認証とホストキーの検証が機能していること。秘密鍵ファイル、ポート、ProxyJump は SSH 設定のエイリアスで指定してください。remote コマンドが受け付けるのはエイリアスまたは `[user@]hostname` で、SSH オプションや URL は受け付けません。
- glibc 2.28 以降を備えた Linux ホストで、SSE4.2 対応の x64 または ARM64 であること。musl/Alpine やその他のリモート OS には対応していません。
- リモートのワークスペースディレクトリがすでに存在し、リモートのホームディレクトリに書き込めること。また、`getconf`、`sha256sum`、GNU 互換の `stat` と `mv` を含む標準的な Linux シェルユーティリティがあること。インストールに sudo やリモートへの Bun のインストールは必要ありません。
- クライアントに信頼済みのサーバーリリースキーがあり、それに対応する署名済みサーバー成果物があること。リリース版クライアントでは、不足している成果物を**手元のコンピューター上で**ダウンロードしてキャッシュします。リモートホストがサーバーバイナリをダウンロードすることはありません。
- 接続には対話型の端末が必要です。`TERM=dumb`、print モード、従来の RPC はリモート用フロントエンドではありません。

Amira は PTY や SSH エージェント転送を使わず、SSH の標準入出力を利用します。通常の SSH 設定で、あらかじめ認証とホストキーの検証を済ませてください。Amira がこれらの確認を回避することはありません。

## 追加と接続

```sh
amira remote add devbox --name project --cwd /home/dev/project
amira remote attach project
```

`add` はホストを調査し、サーバーをインストールして、接続先をローカルに保存します。UI は開きません。インストールと今後のバイナリの自動更新を承認する前に、表示される SSH ユーザー、インストール先、サーバーのバージョン/ビルド、モデルモードを確認してください。`attach` でホストを直接セットアップすることもできます。

```sh
amira remote attach devbox --cwd /home/dev/project
```

`--cwd` には Linux の絶対パスを指定してください。`~` やローカルのパスは使えません。省略した場合、既存の接続先では保存済みのワークスペースを、新しいホストではリモートのホームディレクトリを使います。接続時に、リモートホスト上でワークスペースの正規パスを解決します。指定したワークスペースは、その接続先のデフォルトとして保存されます。接続先の名前は英字または数字で始まり、英字、数字、ドット、アンダースコア、ハイフンのみで構成し、128 文字以内にしてください。

対話なしでインストールに同意するには、`--accept-install`（別名 `--yes`）を使います。これはインストールと自動更新を許可するもので、プロバイダーのバインディングを承認するものではありません。`attach` には引き続き端末が必要です。

```sh
amira remote add devbox --name project --cwd /home/dev/project --accept-install
```

オフラインの成果物を使う場合は、必要な呼び出しごとにローカルのバンドルディレクトリを指定します。

```sh
amira remote attach project --bundle /path/to/signed-server-bundle
```

このディレクトリには、`server-manifest.json`、その base64 形式の Ed25519 署名である `server-manifest.json.sig`、対象プラットフォームの未加工の実行ファイル（`amira-server-bun-linux-x64-baseline` または `amira-server-bun-linux-arm64`）を含めます。マニフェストはクライアントのバージョンと明示的なビルド ID に一致する必要があります。バンドル自体から信頼キーを提供することはできません。開発用チェックアウトでは、署名済みのローカルバンドルと、開発用の明示的な `AMIRA_SERVER_BUILD_ID` が必要です。パッケージのバージョンだけでは不十分です。

リモート用のオプションは `amira remote --help` で確認できます。`--model`、`--resume`、`-p`、`--extension` など、通常の起動フラグは `remote add` や `remote attach` では使えません。`add` 専用なのは `--name` のみで、ここに記載したその他のリモート用オプションは両方に適用されます。クライアントに `remote list`、`remote remove`、`remote stop` コマンドはありません。

## モデルと認証情報

### デフォルト：ローカルのプロバイダー接続

モデルはリモートの設定で選択します。サブエージェント、タイトル生成、圧縮に使うモデルも含まれます。[プロバイダー](providers.md)と[設定](settings.md)を参照して、リモートホスト上でプロバイダー/モデルの参照を設定し、対応するプロバイダーの認証情報を手元のコンピューター上で設定してください。バインディングには、ローカルでも同じプロバイダー ID とプロトコル（`dialect`）が必要です。Amira がリモートのモデル一覧をローカルの一覧に置き換えることはなく、汎用的なプロバイダーのエイリアスマッピングも提供しません。

UI が開く前に、リモートのプロバイダーが特定のローカルのプロバイダーアカウントとエンドポイントを使ってよいか、Amira が確認します。想定されるリモートのエンドポイント、ローカルのエンドポイント、課金先のアカウントを確認してください。この承認はリモートツールの承認とは別です。ローカルのアカウントでモデルリクエストを行うことを許可しますが、キーそのものへのアクセスは許可しません。ローカルのキーの送信先をリモートのエンドポイントが決めることはありません。

承認記録は、ローカルの Amira ホーム内の `remote/bindings` に留まります。記録に含まれるのはハッシュで、プロバイダーキー、ヘッダー、認証情報を含む URL は含まれません。記録の有効範囲は SSH 接続先/ワークスペースとバインディングの識別情報に限定されます。認証情報、エンドポイント、リモートのプロバイダーの識別情報を変更すると、対応する承認は無効になります。バインディングがない場合や承認を拒否した場合、そのモデルは利用できません。ローカルで設定して承認した後、接続し直してください。リモートの認証情報への自動フォールバックはありません。

推論に必要なプロンプト、ツールの結果、画像は、ローカルのメモリーを経由してプロバイダーに渡ります。キーをローカルに留めても、ワークスペースの内容が手元のコンピューターやプロバイダーに渡らないという意味ではありません。

### 明示的にリモートの認証情報を使う

```sh
amira remote add devbox --name remote-models --cwd /home/dev/project --remote-key
amira remote attach remote-models
```

`--remote-key` はリモートホスト上に設定されたプロバイダーの認証情報を使い、そこでプロバイダーリクエストを行います。ローカルのプロバイダーキーをコピーすることはありません。選択したモードは接続先への同意情報とともに保存されます。以後その接続先に接続するときは、フラグがなくても remote-key モードを維持します。フラグを省略しても local-proxy モードには戻りません。現在、`--local-proxy` スイッチはありません。

稼働中のデーモンは、起動時のモデルモードを維持します。接続先への同意情報を変更しても、実行中のプロセスは変わりません。別のモードでワークスペースを起動する前に、実行中の作業を確認したうえで明示的に停止してください。互換性のない接続は拒否され、認証情報が通知なしで切り替わることはありません。

## どちらのコンピューターが何を担当するか

| リモートホスト | 手元のコンピューター |
| --- | --- |
| エージェント、組み込みツール、シェルコマンド、ジョブ、サブエージェント、ワークスペースのファイル | 全画面描画、クリップボード、外部エディター、端末操作 |
| エージェントの設定、プロバイダー/モデルの定義、権限、信頼、指示、スキル、MCP の設定 | ユーザーレベルのテーマ、キー割り当て、`tui` 設定。ローカルのプロジェクト設定やテーマは読み込みません |
| 保存済みの会話と、`/resume`、`/clear`、フォーク、巻き戻しなどのセッション操作 | ローカルの Amira ホームの `remote` ディレクトリ内にある SSH 接続先の記録、成果物のキャッシュ、プロバイダーのバインディング承認記録 |
| 明示的な remote-key モードの場合に限り、プロバイダーの認証情報 | デフォルトの local-proxy モードでのプロバイダーの認証情報と HTTP リクエスト。入力履歴はメモリー内に留まります |

リモートホストでは、通常の[設定の優先順位](settings.md)が適用されます。ローカルの設定を丸ごと同期したり転送したりすることはありません。`AMIRA_HOME` はローカルの Amira ホームを指定します。SSH インストーラーはリモートユーザーの `$HOME/.amira/remote` を使い、ランチャーは `$HOME/.amira/remote/bin/amira-server` に配置されます。

リモートモードで実行されるのは、同梱の実行可能な拡張機能だけです。インストール済み、または明示的に設定された実行可能な拡張機能は、通知を表示してスキップします。それらのカスタムツール、コマンド、ビューがリモートに対応するわけではありません。信頼済みパッケージのスキルデータは、引き続きリモートで検出できます。同梱のプロファイルにはツール、スキル、MCP、web、ステータス、サブエージェントが含まれますが、`/provider` や `/ext` による管理は含まれません。リモートのプロバイダー設定やパッケージは、接続中の UI の外で管理してください。ローカルにインストールされた拡張機能も、リモート用フロントエンドでは実行されません。[拡張機能](extensions.md)を参照してください。

## ファイル、画像、リンク

- `@` 補完は**リモート**のファイルを一覧表示します。サブエージェント/ワークツリーにフォーカスしている場合は、適切なリモートのスコープが使われます。ローカルのチェックアウトを参照することはありません。
- `@` でリモートの画像を選ぶと、リモートホストから読み込みます。貼り付けやドロップで指定したローカルの画像パスとクリップボードの画像は、ローカルで読み込んでバイト列としてアップロードします。ローカルの相対パスの基準は、リモートのワークスペースではなく、クライアントを起動したディレクトリです。開く対象のファイルとしてローカルのパス名をサーバーに渡すことはありません。
- 通常の対応画像形式と、**1 メッセージあたり合計 5 MB** の上限が適用されます。選択したモデルが画像に対応している必要があります。[画像](usage.md#画像)を参照してください。
- リモートのファイルパスはテキストとして表示され、クリックできるローカルのファイル/エディターへのリンクにはなりません。リモートモードで端末のハイパーリンクを有効にするのは、HTTP(S) のリンク先だけです。

ファイル同期、ポート転送機能、リモートエディターとの連携、コンテナーランチャー、WSL ランチャーはありません。ローカルのエディターを開いて編集するのは、ローカルの下書きであり、リモートのプロジェクトファイルではありません。

## 切断、停止、再接続

リモートユーザーとワークスペースの正規パスの組み合わせごとに、1 つのデーモンが管理します。アクティブなメインの会話と操作権を持つクライアント（コントローラー）は、それぞれ 1 つです。閲覧専用モードや複数コントローラーの同時接続には対応していません。操作権が保持されている間は、別のクライアントは拒否されます。接続が閉じた後も、操作権は最大 30 秒間予約されるため、新たな接続には待機が必要な場合があります。この切断後の猶予期間を過ぎると、再接続用の認証情報は絶対的な最長有効期限の 24 時間を待たずに無効になります。どちらかの期限を過ぎたら、終了して `amira remote attach` を再実行してください。`/reconnect` では期限切れの操作権を復旧できません。

- **切断：** `/quit` はローカルの UI を終了して切断します。デーモン、実行中のツール、バックグラウンドジョブ、サブエージェント、保留中のリモートの承認/質問は停止しません。端末を閉じると、ローカルのモデルブローカーも失われます。
- **ターンの停止：** Esc は現在のターンを停止します（スラッシュコマンドが実行中なら、先にそのコマンドをキャンセルします）。すべてのバックグラウンドジョブやサブエージェントを停止するわけではありません。それらには `/tasks` と `/agents` の操作を使ってください。
- **ワークスペースの停止：** 次のコマンドを、同じ SSH ユーザーで**リモートホスト上で**実行します。これはデーモンとその実行中の作業を意図的に停止するもので、切断コマンドではありません。

```sh
"$HOME/.amira/remote/bin/amira-server" stop --cwd /home/dev/project
```

SSH が一時的に中断すると、自動再接続を行います。新たな接続のたびにセットアップの状態を調査し、署名済みの成果物を再確認します。認証/ホストキーの検証の失敗、リモートの識別情報/プラットフォームの変更、成果物の拒否、インストールエラー、デーモンの非互換があると、自動再試行を停止して復旧方法を案内します。原因を修正してから、ローカルの `/reconnect` を使ってください。承認を変更する必要がある場合は、切断して `remote add` を再実行し、内容を確認してください。`/reconnect` が同意を与えたり、検証を回避したりすることはありません。

local-proxy モードでは、リモートのツール/ジョブはクライアントなしでも継続できますが、次のモデルリクエストは受け入れ済みのローカルブローカーを待ちます。デフォルトの待機時間は 10 分です。期限切れになると、影響を受けるターンはユーザーによる中断ではなく、ネットワーク障害として終了します。すでに試行したプロバイダー呼び出しを再開できるのは、保持期間の範囲内で、同じローカルプロセスが保持している同じ呼び出しに限られます。その呼び出しを失った後、新たな有料リクエストとして自動的に再発行することはありません。クライアントを終了したり、クライアントがクラッシュしたりすると、そのブローカーのメモリーは失われます。新たな接続では、以前のプロバイダーストリームを復元できません。remote-key モードはローカルブローカーに依存しません。

稼働中のデーモンへの再接続は、保存済みの会話履歴を選ぶ `/resume` やデーモンの再起動とは異なります。再生用のイベントはメモリー内にのみ保持され、上限は **32 MiB または 50,000 イベント**のうち、先に到達した方です。カーソルの期限が切れたり、デーモンのエポックが変わったりすると、スナップショットで再同期します。その時点で残っている進行中/保留中の状態も含まれますが、過去の一時的なイベントをすべて復元するわけではありません。保存済みのセッションは、無制限のイベントジャーナルではありません。

デーモンのクラッシュ、ホストの再起動、アイドル状態での終了の後は、新しいデーモンがワークスペースの最新の保存済み会話を開きます。実行中だったツール、OS プロセス、ジョブ、承認ダイアログ、プロバイダーストリームを復活させることはできません。利用できるのは、すでに保存された履歴だけです。再接続はクラッシュからの復旧ではありません。

### タイムアウト

次の設定は、ローカルのフロントエンド設定ではなく、**リモートホスト上で**行ってください。

```json
{
  "remote": {
    "idleTimeoutMs": 1800000,
    "proxyReconnectTimeoutMs": 600000
  }
}
```

`idleTimeoutMs` のデフォルトは 30 分で、切断され、実行中の作業、保留中のモデル呼び出し、承認/質問、ジョブがない、完全なアイドル状態の場合にのみ適用されます。そのため、保留中の承認があると、デーモンは無期限に稼働し続ける場合があります。`proxyReconnectTimeoutMs` のデフォルトは 10 分で、ローカルのモデル接続を待つ時間を制御します。操作権の猶予期間や、受け付け済みの呼び出しの保持期間ではありません。どちらも `0` から `2147483647` までの整数のミリ秒を受け付けます。`0` を指定すると、前者はアイドル時の終了を無効にし、後者はプロキシの受け入れを無期限に待ちます。アイドルタイムアウトはデーモンの起動時に読み込まれます。設定の再読み込みで今後のプロキシ待機時間を更新できますが、すでに試行した呼び出しを再実行したり、ブローカーの保持期間を変更したりすることはありません。

## 更新

セットアップへの同意には、その SSH の識別情報/インストール先とモデルモードに対応する、今後の署名済みバイナリの更新も含まれます。接続のたびに、ローカルの成果物の署名、サイズ、ハッシュ、ビルドの識別情報を検証します。アップロードした内容はリモートでも再確認してから、ランチャーをアトミックに置き換えます。更新に失敗しても、それまで動作していたランチャーとビルドは保持されます。

新しい実行ファイルをインストールしても、稼働中のデーモンは停止**しません**。互換性のある実行中のビルドには、インストール済みと実行中のバージョン/ビルド ID を示す通知を表示したうえで、接続を維持する場合があります。置き換えは、そのワークスペースにコントローラー/リレー接続がなく、実行中の作業や保留中のリクエストもなくなるまで待ちます。作業を終えて切断し、デーモンを終了させてから、もう一度接続してください。実行中のビルドに互換性がない場合は、接続を拒否します。アイドル状態での終了を待つか、影響を確認したうえでワークスペースを明示的に停止してください。非互換を回避するために、Amira が 2 つ目の管理用デーモンを起動することはありません。

## 明示的な参加による Linux/SSH メンテナーチェックリスト

これは手動で行うプラットフォームの受け入れ判定であり、自動化されたオフライン CI の一部では**ありません**。また、Linux や実際の SSH で検証済みだと主張するものでもありません。Windows ネイティブのテスト用フィクスチャーや偽の SSH だけでは、Linux x64/ARM64 への対応は確認できません。メンテナーが明示的に実施を選択した場合に限り、使い捨てのホスト/ワークスペースと、分離したクライアント/サーバーのアカウント/ホームディレクトリを使って実行してください。メンテナーが管理する決定論的なモックのモデルエンドポイントとダミーの認証情報を使い、実際のプロバイダーへのアクセスを遮断してください。実際のプロバイダーで料金を発生させる必要はありません。このモックエンドポイントはテスト用フィクスチャーであり、リモート CLI のフラグではありません。

- [ ] クライアント/サーバーのバージョン、ビルド ID、署名済み成果物のハッシュ、アーキテクチャー、ディストリビューション/glibc、CPU、OpenSSH のバージョンを記録します。Bun や Node をインストールしていない環境で、実際の Linux x64 と ARM64 の成果物をそれぞれ実行し、プロセス/stdout ワーカーとシェルツールを検証してください。クロスコンパイルだけでは合格になりません。設定を読み込まない `--version-json` と `--self-check` を確認します。
- [ ] 実際の OpenSSH のエイリアス、明示的なユーザー/ポート/鍵の設定、ProxyJump を試します。未知のホストキー、変更されたホストキー、認証の失敗によって、検証が回避されたり、無期限に再試行されたりしないことを確認します。PTY やエージェント転送を要求しないことを確認します。空白/引用符を含むパス、stderr のバナー、非ログイン時の PATH を試し、stdout が有効な JSONL のままであることを確認します。
- [ ] glibc/CPU が要件を満たさない場合の拒否、必要なユーティリティ、ホームディレクトリの所有者/権限、ローカルファイルシステム上の非公開のソケット/メタデータ/ログ、長いワークスペース/ソケットのパス、古い PID/ロックからの復旧、XDG ランタイムのフォールバックを確認します。別のユーザーが接続したり、メタデータを置き換えたり、非公開のログを読んだりできないことを検証します。合格させるために権限を緩めないでください。
- [ ] リモートでのダウンロードを遮断した状態で、署名済みのローカルバンドルを使ってインストールします。実際のアップロードを中断し、ホームの容量不足や noexec マウント、チェックサムツールの欠落、バンドル/ハッシュ/署名の破損、同時セットアップを試します。障害が起きても動作するランチャーが保持され、検証済みで一致するバイト列だけが公開されることを確認します。
- [ ] リモート/ローカルで一致するモックモデルの ID/プロトコルを設定します。ローカルでバインディングを承認し、承認の拒否、バインディングの欠落、エンドポイント/認証情報の変更、承認記録の無効化を試します。取得するのはダミーの検出用マーカーだけにし、それらがリモートプロトコルの入力、セッション、ログに認証情報として現れないことを確認します。ローカルのキーへのフォールバックなしで、remote-key モードを別途テストします。
- [ ] 組み込みツールでファイルを編集し、長時間実行するリモートシェルジョブを動かします。承認、質問、ライブフォーム、サブエージェントへのフォーカス/停止、ジョブの出力/停止、セッションの切り替え、ステータス/使用量、画像を使った実行中の指示を試します。スキップした実行可能な拡張機能が報告され、実行されないことを確認します。リモートの `@` ファイル/画像と、操作できないファイルリンクを検証します。
- [ ] 作業中およびダイアログの保留中に SSH リレーだけを切断し、操作権の猶予期間内に再接続します。プロンプト、承認、フォームの操作/送信、有料呼び出しの開始が重複せず、ジョブ/ターンが意図せず中断されないことを確認します。オフラインでのフォーム編集/保存/キャンセルと、古くなった回答を試します。
- [ ] 現実的な遅延、大きなファイル一覧/画像アップロード、頻繁に出力するジョブ、大量の出力とバックプレッシャーを試し、メモリー使用量の上限、入力の応答性、キャンセルが後回しにならないことを確認します。途中で切れたフレーム/EOF、不正な形式の完全なフレームも試します。再生用イベントの保持上限を超え、フロントエンドの操作を再実行せずにスナップショットで復元できることを確認します。2 つ目のコントローラーと、操作権の猶予期間/トークンの有効期限を過ぎてからの再接続を試し、新たな接続による復旧方法が具体的に案内されることを確認します。
- [ ] プロキシの中断中もクライアントを稼働させ続け、その後、ブローカーの保持期間切れと、クライアントプロセスのメモリーの喪失を別々に試します。プロキシが受け入れられないと、ターンがネットワーク障害として一度だけ終了し、無関係なジョブは継続することを確認します。受け付け済みの呼び出しが無条件に再発行されないことを確認します。
- [ ] `/quit`、ターン/ジョブ/サブエージェントの停止、明示的なワークスペースの停止を比較します。切断後のアイドル時の終了、保留中の承認によるデーモンの稼働継続、タイムアウトの上書き、ゼロの値を確認します。
- [ ] 作業の実行中に、新しい署名済みビルドをインストールします。インストール済み/実行中の通知、互換性がある場合の作業完了と切断後の終了、互換性がない場合に 2 つ目のデーモンや強制停止なしで接続を拒否する動作を確認します。同じビルド ID を持つ異なるバージョンも含めます。
- [ ] 実際のホストのポリシーの下で、SSH のログアウト/SIGHUP、セッションマネージャーによるクリーンアップ、デーモンの強制終了、ホストの再起動を試します。戻るのは保存済みの履歴だけで、実行中のプロセス/ダイアログ/ストリームは戻らないことを確認します。プロセスの復活を保証せず、孤立したプロセスの処理を調べます。
- [ ] 各プラットフォーム/ケースを合格、不合格、未実施として記録し、機密情報を除去した証拠と残る未検証事項を添えます。実際の Linux/SSH の結果は、オフラインのコーデック/モックテストや、ネイティブ Windows のパッケージング結果とは分けてください。

ログインマネージャーによっては、ログアウト時にそのユーザーの全プロセスを終了します。SSH からの切断でホストのポリシーを回避することはできません。必要であれば、管理者が承認したユーザーレベルの監視サービスや linger ポリシーを使い、別途検証してください。Amira のインストール自体に sudo は不要です。
