# サブエージェント

[English](../subagents.md) · [简体中文](../zh/subagents.md) · [ドキュメント](../../README.ja.md)

同梱の agent 拡張機能は、別のエージェントにタスクを委任する `agent` ツールと、必要に応じて結果を収集する `agent_result` ツールをモデルに提供します。委任は通常の言葉で依頼できます。これらはモデル用のツールであり、スラッシュコマンドではありません。

たとえば、「explorer にリクエストハンドラーを追跡してもらい、reviewer にエラー処理経路を調べてもらってください。その間もテストの確認を続けてください」と依頼できます。各タスクには、明確な目標、関連するパス、制約、求める報告内容を指定してください。

## タスク・ロール・コンテキスト

一回の `agent` 呼び出しで複数のタスクを開始できます。各タスクには、短いタイトルと十分な情報を含むプロンプトが必要です。タスクにはロール、モデル、コンテキスト、分離方法を指定できます。ロールを省略すると、親で利用可能なツールを使う汎用エージェントを開始します。

| 組み込みロール | 用途 |
| --- | --- |
| `explorer` | コードベース全体を読み取り専用で調査します |
| `coder` | 利用可能なツールを使い、明確に指定された変更を実装します |
| `reviewer` | 正しさに関する問題を読み取り専用でレビューします |

explorer と reviewer のロールには、制限されたツール一覧と、シェルツールを読み取り専用コマンドにだけ使う指示があります。ただし、OS レベルのサンドボックスではありません。デフォルトでは、すべてのロールが共有ディレクトリで作業します。`coder` でも、worktree が自動で与えられるわけではありません。

`context` のデフォルト値は `"fresh"` です。子エージェントは、独自の会話でタスク、ロール、プロジェクトの指示を受け取ります。親の会話も必要な場合は `"fork"` を使ってください。子は最終回答と変更内容を親に報告します。fresh コンテキストを使う場合は、明示していない会話の内容を子が見ていると考えないでください。

モデルの優先順位は、タスクの `model`、設定の `agents.<role>.model`、ロールファイルの `model`、親のモデルの順です。[設定](settings.md)を参照してください。

### カスタムロール

ロールファイルは、ユーザーディレクトリの `agents/` フォルダー、またはプロジェクトの `.amira/agents/` フォルダーに置く Markdown ファイルです。同じ名前のロールでは、プロジェクトのロールがユーザーのロールを上書きし、ユーザーのロールが組み込みロールを上書きします。frontmatter が不正なファイルは、報告してスキップします。

たとえば、`.amira/agents/test-reviewer.md` を作成します。

```markdown
---
name: test-reviewer
description: Review tests for missing cases
tools: [read, grep, glob]
---
Review the tests named in the task. Do not edit files.
Report missing cases with file paths and concrete examples.
```

frontmatter は `name`、`description`、`model`、`tools`、`isolation` に対応しています。名前のデフォルト値はファイル名です。`model` は provider/model の形式を使います。`tools` はリストまたはカンマ区切りの文字列にでき、`isolation` には `none` または `worktree` を指定できます。本文は、そのロールの指示になります。ロールによって、親セッションで無効になっているツールが有効になることはありません。

## バックグラウンド実行と制限

デフォルトでは、メインセッションの `agent` 呼び出しは、モデルが処理の完了を待つ呼び出しを要求しても、子の ID を返してすぐに終了します。メインエージェントと会話している間も、子は作業を続けます。子の報告は自動で届きます。ターンの実行中は次のモデルリクエストの前に追加され、待機中はフォローアップのターンを開始します。近いタイミングで完了した報告は、一つのメッセージとして届く場合があります。

このデフォルトのメインセッションの動作では、`agent_result` は待機せず、進捗を報告するか、すでに利用可能な結果を収集します。結果は一度だけ届けられます。`subagents.background` を `false` に設定すると、デフォルトで完了を待つ呼び出しに戻ります。個々の呼び出しでは引き続き `background: true` を指定できます。子エージェント自身の呼び出しは、デフォルトで完了を待ちます。バックグラウンドタスクを使う場合は、拡張機能が管理する永続的な子でない限り、終了前に結果を収集する必要があります。

Esc はメインのターンを中断しますが、バックグラウンドの子は作業を続けます。停止するには `/agents stop <n|id>` または `/agents stop all` を使ってください。手動で停止した子の報告は、新しいモデルのターンを開始せず、次のユーザーメッセージまで待機します。`/clear`、セッションの切り替え、終了では、閉じた会話のサブエージェントとそのバックグラウンドジョブを停止します。セッションを切り替える場合、会話自体の最上位のバックグラウンドジョブは新しいセッションに引き継ぎます。[print モードと RPC モード](usage.md#print-モード)では、Amira はバックグラウンドの結果と、その結果が開始するターンの完了を待ってから正常終了します。

デフォルトでは、メインエージェントの下に二段階までのネストを許可し、**エージェントツリー全体で**同時に四つの子が作業できます。それを超えるタスクはキューに入ります。変更するには `subagents.maxDepth` と `subagents.maxConcurrent` を設定してください。子の完了を待っている親は、作業スロットを占有しません。`budget.tokens` と `budget.costUsd` は、メインエージェントを含むツリー全体を制限します。デフォルトでは予算を設定しません。トークン予算には、入力、出力、キャッシュの読み取りと書き込みを含めます。費用の予算は、報告された費用に依存します。予算を超えると、実行中の子を停止し、新しい子の開始を拒否します。

子は親と同じ権限モードとルールで動作し、"Don't ask again" で与えた承認を共有します。[権限ポリシー](usage.md#権限)が子のツール呼び出しについて確認する場合、質問は親のモデルではなく、あなたに届きます。そのため、エージェントが子に許される操作を広げることはできません。拡張機能が子について出す承認要求は、親のモデルに届きます。子の質問にも親が回答し、必要に応じてユーザーに取り次ぐことができます。最上位の承認ダイアログについては、[使い方](usage.md#ツールと承認)を参照してください。

## 一覧と閲覧

| コマンド | 操作 |
| --- | --- |
| `/agents` | 閲覧する子、またはレビューする保持済みの worktree を選びます |
| `/agents <n|id>` | 子の会話記録を会話に出力します |
| `/agents view` | 実行中の最新の子を表示します。なければ、最新の子を表示します |
| `/agents view <n|id>` | その子のライブビューアーを開きます |
| `/agents stop <n|id>` | 実行中の子を一つ停止します |
| `/agents stop all` | 実行中のすべての子を停止します |
| `/agents worktrees` | このリポジトリの保持済みの worktree を一覧表示します |

参照には、1 から始まる一覧の番号、完全な ID、一意に特定できる ID の接頭辞を使えます。行には、タイトル、ロール、状態、経過時間、トークン数、判明している場合は費用を表示します。対話型の選択画面では、Enter で子を開き、`p` で代わりにその会話記録を出力します。print モードでは項目をテキストで一覧表示し、ライブビューアーには対話型 UI が必要です。

ビューアーは、子の作業に合わせて更新されます。←/→ または Tab/Shift+Tab で子を切り替えます。`p` で表示中の会話記録を出力し、`x` で表示中の子の停止を確認し、`y` で確定します。ほかのキーを押すと、その停止を取り消します。Esc、`q`、Ctrl+C でビューアーを閉じます。背後でメインセッションのダイアログが待機している場合は、そのことも表示します。ビューアーはどちらの端末モードからも使えます。インラインモードでは、一時的に代替画面を使います。

## worktree とマージ

実装タスクには `isolation: "worktree"` を使うようエージェントに依頼するか、ロールに `isolation: worktree` を指定してください。Amira は、未コミットの追跡対象の変更も含め、親の現在の追跡対象ファイルから、ブランチに接続しない Git worktree を作成します。**未追跡のファイルはコピーしません。** Git リポジトリの外や最初のコミット前など、worktree の作成に失敗した場合は、共有ディレクトリでの作業に切り替え、その事実を報告します。

正常に完了した子の変更は、パッチとして収集し、親の作業ツリーに適用します。競合のないパッチは、デフォルトで自動適用します。マージは一つずつ順番に行います。これによって親のブランチにコミットが作成されることはありません。`merge.reviewThreshold.lines` と `merge.reviewThreshold.files` を使うと、どちらかの上限を超える競合のないパッチにレビューを要求できます。

競合がある場合は、次の選択肢を持つ差分レビューを開きます。

- `Apply what fits (.rej files for the rest)`: 一致するハンクを適用し、拒否されたハンクは `.rej` ファイルに残して、worktree を保持します。
- `Keep in the worktree`: 後でレビューできるよう、ファイルとパッチを保持します。
- `Discard`: 子の worktree と変更を削除します。

レビューが必要な競合のないパッチでは、部分適用の代わりに `Merge` を提示します。取り消した場合や回答できない場合は、worktree を保持します。失敗または停止した子では、未完了の変更をマージせずに保持します。結果には、worktree とパッチのパスを示します。共有ディレクトリのタスクによる編集は、すでにあなたのディレクトリに反映されているため、マージするための分離されたパッチはありません。

`/agents` を開き、保持済みの worktree を選ぶと、現在の差分のレビュー、マージ、保持、破棄ができます。後からのマージで競合が起きた場合は、何も適用せず worktree を保持します。`/agents worktrees` は一覧表示だけを行い、レビュー用の選択画面は開きません。

保持済みの worktree は、クリーンアップの対象です。操作のない状態が七日続くと削除予定を通知し、少なくともさらに一日経過してから削除します。クリーンアップは継続的には行わず、このリポジトリで別の子に worktree を作成する際に実行します。`Keep` を選ぶと、保持期間を最初から数え直します。使用中の worktree は対象外です。

## workflow と swarm の拡張機能

二つの公式拡張機能がサブエージェントを活用します。これらは Amira には同梱されていません。[CAMB-dev/amira-extensions](https://github.com/CAMB-dev/amira-extensions) にあり、ほかのパッケージと同じ方法でインストールします（[拡張機能](extensions.md)を参照してください）。

```sh
amira ext install workflow
amira ext install swarm
```

- [workflow](https://github.com/CAMB-dev/amira-extensions/tree/main/extensions/workflow/README.md) は、`/workflow` と `workflow` ツールを追加します。多くのサブエージェントをバックグラウンドで連携させる TypeScript スクリプト（並列展開、検証、パイプライン）を実行でき、進捗表示（`/workflow view`）や実行記録からの再開に対応します。スクリプトは `.amira/workflows/` またはユーザーディレクトリの `workflows/` に保存します。デフォルトでは、一回の実行で合計 30 エージェント、同時に 6 エージェントを開始できます。
- [swarm](https://github.com/CAMB-dev/amira-extensions/tree/main/extensions/swarm/README.md) は、`/swarm <goal>` と `swarm` ツールを追加します。少数の長時間稼働するメンバーが、共有のブラックボードとメッセージを使って一つの目標に取り組み、`/swarm view` で状況を確認できます。予算を設定しない場合、swarm は 3,000,000 トークンを消費する可能性があります。

どちらも、`/workflow <task>`、`/swarm <goal>`、またはメッセージで依頼できます。役立つ場合はモデルから提案することもあります。デフォルトでは、開始するたびに計画と制限を表示して確認を求めます。print モードなど、誰も確認できない環境では、モデルは開始できません。開始できるのはメインセッションだけです。設定は `extensions.workflow` と `extensions.swarm` にあります（`enabled` は `"ask"`、`"always"`、`"never"` で、ほかに制限と予算があります）。各拡張機能の制限は、前述のツリー全体の `subagents` と `budget` の制限内で適用されます。詳細なリファレンスは各拡張機能の README を参照してください。
