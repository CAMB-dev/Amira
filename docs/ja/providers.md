# プロバイダーとモデル

[English](../providers.md) · [简体中文](../zh/providers.md) · [ドキュメント](../../README.ja.md)

プロバイダーは、プロトコル、エンドポイント、認証情報を組み合わせたものです。最初のタスクを送信する前に追加してください。models.dev カタログにあるベンダーのデフォルト値を使うと、設定しやすくなります。モデルは `provider/model` の形式で選択します。プロバイダー名には、自分で割り当てた ID を使います。

## プロトコルの選択

| プロトコル | 用途 | ベース URL の例 |
| --- | --- | --- |
| `openai-chat` | OpenAI 互換のチャット補完。多くのプロキシやローカルサーバーも含みます | `https://api.openai.com/v1` |
| `openai-responses` | OpenAI Responses | `https://api.openai.com/v1` |
| `anthropic-messages` | Anthropic Messages | `https://api.anthropic.com` |
| `google-gemini` | Google Gemini | `https://generativelanguage.googleapis.com/v1beta` |

そのプロトコル向けにサービスが提供しているベース URL を使ってください。互換チャットエンドポイントが、Responses や Anthropic の機能も実装しているとは限りません。

## 追加・編集・削除

対話型セッションでは、`/provider` で管理ページを開き、ID、プロトコル、ベース URL、モデル数、キーの取得元と既知の接続テスト結果を確認できます。**+ Add provider** で追加し、既存のプロバイダーでは **Use a model from it**、**Edit**、**Set key**、**Test connection**、**Remove** を選べます。Esc で閉じます。print（`-p`）と RPC では引き続き一覧表を出力します。

`/provider add` は、先頭に **Vendor** がある一画面のフォームを開きます。**Popular** と **All vendors** を名前や ID で検索するか、**Custom (choose protocol)** を選びます。一覧は models.dev のキャッシュから読み込み、ネットワークを待ちません。ベンダーを選ぶと ID、プロトコル、URL、キーの環境変数名とモデル一覧を入力します。後からベンダーを変更しても、手動編集したフィールドは上書きしません。プロトコルは常にフォーム内で変更でき、別の選択画面はありません。ID が重複した場合は `-2` などを提案します。`/provider add deepseek` または `/provider add openai-chat` で事前選択もできます。

ID、プロトコル、ベース URL、キーの取得元を確認してください。デフォルトでは保存済みの API キーを使い、入力内容はマスクされます。ベンダーに登録されている環境変数のいずれかが設定されている場合、フォームは環境変数による認証を選択し、値ではなく変数名だけを表示します。そうでない場合は、環境変数による認証を選ぶと、一覧の最初の変数名が事前入力されます。

全画面フォームはベース URL と認証情報がそろうとモデルを自動取得します。HTTPS とループバック HTTP はそのまま取得し、それ以外の HTTP は暗号化せずに認証情報を送ることへの明示的な同意が必要です。編集時も、元のモデル一覧が空なら自動取得します。**Fetch models** で手動更新でき、カスタム ID と選択済みモデルは保持されます。一覧はプロバイダーから取得し、models.dev がコンテキストと価格を補います。一問ずつのダイアログでは取得を明示的に選択します。

**Models** の複数選択一覧では、入力すると ID とラベルを大文字・小文字を区別せず部分一致で絞り込みます。Backspace で `filter:` 行を編集します。↑↓ で移動、Space で選択を切り替え、**Ctrl+A** でフィルターに一致する項目をすべて選択します（すべて選択済みなら解除）。**Ctrl+X** は一致する項目の選択を反転します。スクロールで画面外にある一致行も対象です。フィルター外の選択は保持されます。見出しには `selected 12/240`、絞り込み中はさらに `· 30 shown` を表示します。Esc は空でないフィルターを先に消し、もう一度押すとフォームをキャンセルします。変更がある場合は破棄を確認します。カスタム値を許可する一覧では、未登録の ID を入力して Enter で追加できます。独立した 2 つの右揃え列に、既知のコンテキストウィンドウとカタログの入力/出力価格（100 万トークンあたりの米ドル）を表示します。幅が足りない場合は価格を先に隠し、次にコンテキストを隠します。カタログにないモデルも残りますが、価格は表示しません。

折りたたまれた **Advanced** には、リクエストヘッダー（1 行に `Name=value`、`${ENV}` を参照可能）、順序付きのキー環境変数フォールバック、プロトコル別の互換設定、モデルごとの `fast` 記述子があります。設定スキーマで対応する項目だけを扱います。編集時は未知のキーと既存のモデル上書きを保持し、キーの取得元を変えてもフォールバックを削除しません。

ライブの **settings.json preview** は書き込む項目を表示し、ヘッダーの秘密値をマスクします。**key → auth.json** も別行でマスクして表示します。広い画面ではフォームの横、狭い画面では下に配置します。Tab で **Preview** に移動し、↑↓、PageUp/PageDown、Home、End で長い項目を確認できます。すべてのフォームでラベルを右揃えにし、入力領域を明確にします。幅が足りない場合はラベルを入力の上に移します。

**Save** は最初に選択したモデルにごく小さな接続テストを送信します。有料または価格不明のモデルでは課金の可能性を確認し、無料と分かっているモデルには課金警告を表示しません。結果はフォーム内に表示します。失敗したら **Save anyway** を選ぶか、項目を修正して再試行します。保存後はそのプロバイダーをハイライトした管理ページに戻り、**Use a model from it** でそのプロバイダーだけのモデル一覧を開けます。ダイアログと非 TTY のシェル設定も同じ順序で質問し、最後にマスク済みの要約とプレビューを表示して確認します。コールバックを使うフォームは、RPC クライアントが静的なネイティブフォームを要求しても、一問ずつのダイアログに切り替わります。非 TTY では複数行の項目を 1 行ずつ入力し、`.` だけの行で終了します。すぐに終了すると現在値を保持し、空行を入力してから終了すると消去します。フラグがそろった非対話コマンドは従来どおりで、テストを追加しません。

`/model` で設定済みの一覧からモデルを選ぶか、`/model <provider/model>` で直接指定してください。一覧は選択を便利にするためのもので、一覧にないモデル ID も選択できます。最初のプロバイダーを保存した後、セッションにまだモデルがなく、そのプロバイダーにモデル一覧がある場合は、Amira が一覧の最初のモデルを選択します。

| セッション内のコマンド | 用途 |
| --- | --- |
| `/provider edit <id>` | エンドポイント、キーの取得元、モデル一覧、デフォルト値を編集します |
| `/provider key <id>` | API キーを保存または置き換えます |
| `/provider remove <id>` | 削除を確認します。保存済みのキーを削除するかどうかは、別途選択できます |

使用中のプロバイダーを削除する前に、`/model` で別のモデルに切り替えてください。

同じフォームはシェルからも利用できます。

```sh
amira provider add
amira provider edit <id>
amira provider key <id>
amira provider remove <id>
amira provider help
```

`amira provider add <vendor-or-protocol>` には、カタログのベンダー ID またはプロトコルを指定できます。名前が重複する場合は、プロトコル名を優先します。対応するベンダーでは、次のコマンドで質問なしにデフォルト値を使って設定できます。

```sh
amira provider add deepseek --key-env DEEPSEEK_API_KEY
```

`--id`、`--base-url`、`--model` で、ベンダーの ID、URL、モデルを上書きできます。未対応のベンダーでは、プロトコルと URL を明示する必要があります。従来のプロトコル指定による手順は変わりません。質問なしで設定するには、プロトコル、ID、URL と、キーのオプションをちょうど一つ指定してください。以下のエンドポイントとモデルを、利用するサービスの値に置き換えます。

```sh
amira provider add openai-chat --id my-provider --base-url https://api.example.com/v1 --key-env MY_PROVIDER_API_KEY --model my-model
```

複数のモデルを登録するには、モデルのオプションを繰り返し指定します。キーのオプションには、パイプ経由でキーを渡す `--key-stdin` と、キーが不要なサーバー向けの `--no-key` もあります。削除時には、`--yes` で質問を省略し、`--keep-key` で保存済みのキーを残せます。後者を指定しない場合、無人での削除では既存の保存済みキーも削除します。

## 認証情報と設定

API キーは `~/.amira/auth.json` に保存するか、環境変数から読み込むことができます。キーを使わない設定も可能です。OAuth には対応していません。対話型のキー入力欄はマスクされます。`AMIRA_HOME` を指定すると、設定や保存済みの認証情報の場所を含め、ユーザーディレクトリが変わります。

API キー欄が空、または空白文字だけの場合は、キーを置き換えません。テストと保存では現在設定されている認証情報を保持し、空白での保存は新しいキーを書き込みません。設定済みプロバイダーの接続テストは通常のリクエストと同じ、現在のメモリ上の認証情報を使います。別のプロセスが auth.json を変更・削除しても、実行中のセッションのテストで使うキーは切り替わりません。下書きで取得元を明示的に変えたり、空でない新しいキーを入力したりした場合は、その変更をテストに反映します。

環境変数のキーを使う場合は、Amira を起動する前にプロセスの環境変数を設定してください。設定には、その値ではなく変数名を `apiKeyEnv` に保存します。リクエスト時には、まずその変数、次に `apiKeyEnvFallbacks` 内の変数を順番に試し、最後にそのプロバイダーの保存済みキーを試します。対話で保存すると、**No key** や環境変数認証を含む選択した `keySource` を、フォールバック一覧の長さに関係なく保存します。一覧を空にしても、再起動後に残っている auth.json キーを意図せず有効にしません。フラグがそろった非対話コマンドは従来の設定形式を保ちます。ベンダーから設定する場合は、カタログにある環境変数名が候補として表示されます。カスタムのプロトコルから設定する場合は、自分で変数名を指定する必要があります。

たとえば、PowerShell では次のように設定します。

```powershell
$env:MY_PROVIDER_API_KEY = "replace-with-your-key"
amira
```

POSIX シェルでは次のように設定します。

```sh
export MY_PROVIDER_API_KEY="replace-with-your-key"
amira
```

ユーザー設定に直接プロバイダーを追加することもできます。次の設定例には、モデル固有のコンテキストウィンドウを含めています。

```json
{
  "model": "my-provider/my-model",
  "providers": {
    "my-provider": {
      "dialect": "openai-chat",
      "baseUrl": "https://api.example.com/v1",
      "apiKeyEnv": "MY_PROVIDER_API_KEY",
      "models": [
        { "id": "my-model", "contextWindow": 128000, "maxOutput": 8192 }
      ]
    }
  }
}
```

プロジェクト設定でモデルのメタデータを調整できますが、エンドポイント、キーの環境変数、フォールバック用の環境変数、ヘッダーはユーザー設定からのみ受け付けます。設定のマージとユーザー設定専用のフィールドについては、[設定リファレンス](settings.md)を参照してください。

## モデルのメタデータとコンテキストウィンドウ

Amira は models.dev カタログを使ってモデルの情報を取得します。`models` に明示した項目はカタログのメタデータより優先され、カタログのメタデータは `defaultModel` より優先されます。メタデータがない場合、コンテキストウィンドウは 128,000 トークン、出力上限は 8,192 がデフォルト値になります。これらのフォールバック値は推定値なので、未知のモデルには実際の上限を設定してください。

プロバイダーのフォームにあるデフォルト値は、カタログに情報がないモデルに適用されます。特定のモデルには、設定で `contextWindow`、`maxOutput`、`caps` を指定してください。`caps` で設定する機能は、サーバーが何に対応しているかを示すもので、モデルにその機能を追加するわけではありません。

`catalogId` を使うと、モデルの詳細（コンテキストウィンドウ、機能、価格）を取得する models.dev のプロバイダーを選択できます。`false` に設定すると、そのプロバイダーではカタログを無視します。`my-gateway` のようなカスタムプロバイダーに `"catalogId": "llmgateway"` を設定すると、モデルのメタデータを借用できます。その際、ゲートウェイのほかのモデルが選択画面、`/model` の一覧、入力補完に追加されることはありません。エンドポイントが提供するモデルを `models` に列挙してください。一方、ID の一致や `gemini` → `google` のような組み込みの対応付けによる、プロバイダー自身のカタログは、これらの一覧にカタログのモデルを追加します。

追加や編集時に、`/provider` はモデル ID から `catalogId` を推定する場合があります。他のカタログを使う場合は保存時に “Model details from …” と表示します。カタログ情報だけでは提供状況を確認できません。保存時の接続テストは最初に選択したモデルを確認します。

## 互換性とネイティブ機能

互換性のオプションは、プロバイダーの `compat` オブジェクトに設定します。

| オプション | 動作 |
| --- | --- |
| `maxTokensField` | チャットの出力上限フィールドです。デフォルト値は `max_tokens` で、`max_completion_tokens` も指定できます |
| `streamUsage` | チャットのストリームで使用量を要求します。デフォルト値は `true` です |
| `thinking` | Anthropic の思考モードです。デフォルト値は `adaptive` です。トークン予算を必要とする互換サーバーには `budget` を指定します |
| `thinkingDisplay` | Anthropic の思考テキストです。`summarized` または `omitted` を指定します。`api.anthropic.com` ではデフォルト値が `summarized` で、それ以外のホストには設定しない限り送信しません。`models[].compat.thinkingDisplay` でモデルごとに上書きできます |
| `webSearch` | ホスト側のウェブ検索を提供します（Responses、Anthropic Messages、Gemini）。モデルの `caps.webSearch` を優先します |
| `compaction` | ネイティブ圧縮です。`auto`、`on`、`off` を指定します。デフォルト値は `auto` です |

思考の表示方法を変えても、課金対象のトークン数は変わりません。`omitted` でも、署名付きの思考ブロックは変更せずに送受信し、読めるテキストだけを非表示にします。思考がデフォルトで有効な Claude 5.x モデルでは、推論の強度を明示していなくても Amira が要約を要求し、サーバーの推論の強度のデフォルト値は変更しません。`/thinking default` はサーバーデフォルトの推論の強度を意味し、思考を無効にする指定ではありません。[Anthropic の思考に関するドキュメント](https://platform.claude.com/docs/en/build-with-claude/thinking)を参照してください。DeepSeek と MiniMax は `display` への対応を文書化していないため、このオプションを設定しない限り、リクエストは変更しません。

ホスト側のウェブ検索は、`openai-responses`、`anthropic-messages`、`google-gemini` で実装されています。ベンダーのエンドポイント、すなわち OpenAI と Amira が Azure OpenAI と認識する URL、`api.anthropic.com`、`generativelanguage.googleapis.com` ではデフォルトで有効です。それ以外のホストではデフォルトで無効です。Gemini が Google Search と Amira のツールを併用できるのは Gemini 3 モデルだけなので、それ以前の Gemini モデルではクライアント側の検索を使います。有効な場合、Amira はそのモデルからクライアント側の `web_search` ツールを隠しますが、`web_fetch` は引き続き利用できます。代わりにクライアント側の検索を使うには、`web.nativeSearch` を `false` に設定してください。これは、ウェブ設定でクライアント側の検索バックエンドを選ぶこととは別の設定です。モデルのカタログには検索料金が記載されていないため、検索を行った応答の費用は、モデルの `cost.webSearch`（検索 1 回あたりの米ドル額）を設定しない限り不明と表示されます。

ネイティブ圧縮は、`openai-responses` と `anthropic-messages` で実装されています。`auto` の場合、それぞれが認識するベンダーのエンドポイント、つまり OpenAI/Azure OpenAI と Anthropic でのみ有効になります。自動圧縮と引数なしの `/compact` は、まずネイティブ圧縮を試し、失敗した場合はテキストの要約に切り替えます。`compact.model` が設定されている場合や、`/compact` に指示を渡した場合は、代わりにテキストの要約を要求します。

ホスト側の検索とネイティブ圧縮を実際に転送するプロキシでは、明示的に有効にしてください。

```json
{
  "providers": {
    "proxy": {
      "dialect": "openai-responses",
      "baseUrl": "http://localhost:8000/v1",
      "apiKeyEnv": "MY_PROVIDER_API_KEY",
      "compat": { "webSearch": true, "compaction": "on" },
      "models": [{ "id": "my-model", "contextWindow": 128000 }]
    }
  }
}
```

ローカルのチャットサーバーを CLI で追加する場合は、`openai-chat`、ローカルのベース URL、`--no-key` を選んでください。サーバーが公開しているモデル ID を入力し、実際の上限を設定します。サーバーが実装している機能だけを有効にしてください。

## 編集ツール

Amira には、既存ファイルを変更するツールが二つあります。`edit` は完全に一致するテキストを置き換え、`apply_patch` は OpenAI の Codex が使う形式の複数ファイルのパッチを適用します（[ツールと承認](usage.md#ツールと承認)を参照してください）。プロバイダーごとに `tools.edit` で選択し、`models[].tools.edit` で特定のモデルだけ上書きできます。

| 値 | モデルに提供されるツール |
| --- | --- |
| `"edit"` | `edit` のみ（デフォルト値） |
| `"apply_patch"` | `apply_patch` のみ |
| `"both"` | `edit` と `apply_patch` |

いずれの場合も `write` は提供されます。`apply_patch` に自動で切り替わるモデルはありません。OpenAI の GPT や Codex モデルなど、パッチ形式を適切に扱えるモデルでは、明示的に有効にしてください。

```json
{
  "providers": {
    "openai": {
      "dialect": "openai-responses",
      "baseUrl": "https://api.openai.com/v1",
      "apiKeyEnv": "OPENAI_API_KEY",
      "tools": { "edit": "apply_patch" },
      "models": [{ "id": "my-other-model", "tools": { "edit": "both" } }]
    }
  }
}
```

この選択は現在のモデルに従います。`/model` で別のプロバイダーやモデルに切り替えると、そのモデルの設定が適用されます。サブエージェントは、自身が使うモデルの設定を使います。設定を変更した後は Amira を再起動してください。プロジェクト設定でも `tools.edit` を設定できます。

`apply_patch` は作業ディレクトリ内にだけ書き込み、その配下のシンボリックリンクやジャンクションを通るパスを拒否します。Bun や pnpm でインストールした依存関係など、ほかのハードリンクを持つファイルはその場で書き換えるため、作業ディレクトリ外を含むすべてのリンクに変更が反映されます。Delete は指定したリンクだけを削除します。Move は新しいファイルを書き込み、元の名前を削除するので、ほかのリンクには元の内容が残ります。一つのパッチで、異なる二つのリンクを通じて同じファイルを操作することはできません。

ブロックは順番に適用され、それぞれが先行するブロックの結果を対象とするため、一つのファイルに複数の `*** Update File:` ブロックを指定できます。Add の後の Update、Update の後の Delete、Move 先に対する Update、連続する Move（`a` → `b` → `c`、または `a` に戻す操作）、Delete の後の Add（またはその逆）は、いずれも使えます。Update、Delete、Move では、その時点で元のファイルが存在している必要があります。Add と Move では、移動先または追加先が存在しない必要があります。条件を満たさない場合、パッチは失敗し、パスを示すエラーを返します。一つのパッチ内で、一つのパスをファイルとディレクトリの両方として使うことはできません。

書き込みを始める前に、すべてのブロックを検証します。書き込みに失敗すると、すでに変更したファイルはすべてのハードリンクを通じて元のバイト列に戻され、新規ファイルとフォルダーは削除されます。エラーには、ロールバックが完了したかどうかを表示します。パッチでファイルを削除する間は、隣接する一時的な `.amira-patch-*` フォルダーにロールバック用のリンクを保持し、処理の最後に削除します。これはエラーへの対策であり、クラッシュへの対策ではありません。また、パッチの実行中にほかのプログラムから中間状態が見える場合があります。
