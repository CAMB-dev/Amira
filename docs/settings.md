# Settings reference

[简体中文](zh/settings.md) · [Documentation](../README.md)

Amira reads its settings from JSON files when it starts. Every key is optional; anything you leave out keeps the default listed below.

## Files and precedence

| File | Scope |
| --- | --- |
| `~/.amira/settings.json` | User settings, for every project |
| `<project>/.amira/settings.json` | Project settings, usually committed with the repository |
| `<project>/.amira/settings.local.json` | Your own settings for this project, usually not committed |

`<project>` is the directory Amira starts in. `AMIRA_HOME` moves the user directory: with it set, the user settings are `$AMIRA_HOME/settings.json`, next to `auth.json`, `keybindings.json`, sessions and installed packages.

Layers apply in this order, each one winning over the ones before: built-in defaults, the user file, the project file, `settings.local.json`, then command-line flags such as `--model` or `--disable-tools`. Objects merge key by key; lists and other values replace what an earlier layer set, so a project's `tools.disabled` replaces the user's list rather than adding to it.

A file that is not valid JSON, or a key with a value of the wrong type, stops Amira with an error naming the file and the key. Unknown keys only produce a warning and are ignored, so a newer settings file still loads. A `$schema` key is allowed. API keys never go in settings files: store them with `/provider` or `amira provider` (they go to `auth.json`) or read them from an environment variable named by `apiKeyEnv`.

## User-only keys

A project file travels with whatever repository you clone, so it may not decide where requests and API keys go, turn on server-side compaction, which sends the conversation to an endpoint in a different form, or decide which packages load and which projects are trusted. These keys are ignored, with a warning, in project files and `settings.local.json`:

- `providers.<id>.baseUrl`, `apiKeyEnv`, `apiKeyEnvFallbacks`, `headers` and `compat.compaction`
- `web.search.exa.url`, `web.search.exa.apiKeyEnv`, `web.search.brave.apiKeyEnv`, `web.search.tavily.apiKeyEnv`, `web.search.searxng.url` and `web.fetch.allowPrivateNetwork`
- `packages.disabled`, `packages.trustedProjects` and `packages.untrustedProjects`
- `mcpTrustedProjects`, which only the user file is read for

A project file may still add a provider's models, metadata and other `compat` options, or choose a model.

## Examples

Add a provider whose key comes from an environment variable, trying a second variable when the first is unset or empty:

```json
{
  "model": "my-provider/my-model",
  "providers": {
    "my-provider": {
      "dialect": "openai-chat",
      "baseUrl": "https://api.example.com/v1",
      "apiKeyEnv": "MY_PROVIDER_API_KEY",
      "apiKeyEnvFallbacks": ["MY_PROVIDER_KEY"],
      "models": [{ "id": "my-model" }]
    }
  }
}
```

Set a model's context window and output limit, for a model the catalog does not know or gets wrong. A project file can do this for a provider the user file defines:

```json
{
  "providers": {
    "my-provider": {
      "models": [{ "id": "my-model", "contextWindow": 200000, "maxOutput": 16384 }]
    }
  }
}
```

Use hosted web search and server-side compaction through a proxy that forwards them (by default both are on only at the vendors' own endpoints):

```json
{
  "providers": {
    "proxy": {
      "dialect": "openai-responses",
      "baseUrl": "http://localhost:8000/v1",
      "apiKeyEnv": "MY_PROVIDER_API_KEY",
      "compat": { "webSearch": true, "compaction": "on" },
      "models": [{ "id": "my-model", "contextWindow": 128000 }]
    }
  }
}
```

Search with Brave, falling back to Exa and then a SearXNG instance:

```json
{
  "web": {
    "search": {
      "backend": "brave",
      "fallback": ["exa", "searxng"],
      "brave": { "apiKeyEnv": "BRAVE_API_KEY" },
      "searxng": { "url": "http://localhost:8080" }
    }
  }
}
```

Compact earlier, at 70% of the context window:

```json
{
  "compact": { "threshold": 0.7 }
}
```

Keys are not set here: they live in `keybindings.json` in the user directory. See [Keybindings](keybindings.md).

## General

| Key | Type | Default | Description | User file only |
| --- | --- | --- | --- | --- |
| `model` | `string` | none | Default model as `"provider/model"`. Without it, Amira uses the resumed session's model, or the first model of the only provider. `--model` and `/model` choose another. |  |
| `shell` | `"auto" \| "bash" \| "powershell"` | `"auto"` | Which shell tools the model gets on Windows: `"auto"` offers both `bash` and `powershell`, `"bash"` or `"powershell"` hides the other one. Elsewhere only `bash` exists. `--shell` wins. |  |

| `maxParallelTools` | `number` | `8` | Most tool calls running at once. |  |
| `backgroundJobs.maxRunning` | `number` | `8` | Background jobs (commands the shell tools start with `background: true`, such as dev servers and watchers) running at once. |  |

## Compaction and retries

| Key | Type | Default | Description | User file only |
| --- | --- | --- | --- | --- |
| `compact.threshold` | `number` | `0.8` | Share of the context window at which automatic compaction starts. |  |
| `compact.model` | `string` | the session's model | A `"provider/model"` that writes text summaries. Setting it always makes compaction a text summary, never server-side. |  |
| `compact.layout` | `"tail" \| "recent-user"` | `"tail"` | Where a server-side checkpoint goes: `"tail"` keeps the last turns verbatim after it; `"recent-user"` compacts everything and puts the most recent user messages (up to about 64k tokens) before it, as Codex does. Text summaries always use `"tail"`. |  |
| `retry.attempts` | `number` | `3` | Retries of a failed model request after the first try; `0` turns retrying off. A request is retried only while nothing has streamed yet. |  |
| `retry.baseDelayMs` | `number` | `1000` | Wait before the first retry, doubling each time; a server's `Retry-After` replaces it. |  |
| `retry.maxDelayMs` | `number` | `60000` | A wait longer than this is not waited out: the error is reported instead. |  |

## MCP servers

The MCP extension reads `mcpServers` from `.mcp.json` in the working directory, then from the user file, the project file and `settings.local.json`; a later entry of the same name replaces an earlier one. Strings may use `${VAR}` and `${VAR:-default}`. Servers from project files (`.mcp.json` included) are trusted only when the project directory, or a parent, is in `mcpTrustedProjects`: otherwise their stdio servers do not start, their HTTP servers get no environment variables, and they cannot replace a server the user file defines.

| Key | Type | Default | Description | User file only |
| --- | --- | --- | --- | --- |
| `mcpServers` | `Record<string, Record<string, unknown>>` | none | MCP servers by name. |  |
| `mcpServers.<name>.type` | `"stdio" \| "http"` | `"http"` if `url` is set, else `"stdio"` | Transport. `"streamable-http"` and `"streamableHttp"` mean `"http"`; the legacy `"sse"` is not supported. |  |
| `mcpServers.<name>.command` | `string` | required for stdio | The program to start. |  |
| `mcpServers.<name>.args` | `string[]` | `[]` | Its arguments. |  |
| `mcpServers.<name>.env` | `Record<string, string>` | none | Environment variables for the program. |  |
| `mcpServers.<name>.cwd` | `string` | none | Working directory for the program. |  |
| `mcpServers.<name>.url` | `string` | required for http | The server's streamable HTTP endpoint. |  |
| `mcpServers.<name>.headers` | `Record<string, string>` | none | HTTP headers sent to the server. |  |
| `mcpServers.<name>.timeout` | `number` | none | Milliseconds a tool call may take. |  |
